# 配置页面与性能分析

配置页位于 `data/www/index.html`，通过 SPIFFS 提供。本次更新采用深色配色、
分区导航、桌面双栏与移动端单栏，统一表单、下拉框、按钮和状态提示。
不引入外部字体、图片、JavaScript 框架或 CDN 依赖。

## 已完成的优化

- 移除卡片的 `backdrop-filter`，减少浏览器背景模糊合成工作。
- 日历拖动、缩放、阈值和对比度变化使用 `requestAnimationFrame` 合并重绘。
  同一帧内的多个输入事件只触发一次处理；上传前仍同步渲染，确保位图使用
  最新参数。此优化减少重复计算，但不降低单次抖动算法的计算量。
- 状态查询改为上一次请求完成后等待 30 秒再调度，避免慢响应时请求重叠。
  查询具有 10 秒超时；隐藏页面停止后续轮询，返回页面立即更新。
- 扫描期间禁用扫描按钮，避免单个页面重复发起扫描。
- 网络名称及操作提示通过 `textContent` 写入，避免将返回文本解析成 HTML。
- 保留浏览器端 360 × 460 黑白位图处理，上传位图仍为 20,700 字节。
- Wi-Fi 扫描不再主动断开 STA、停止重连计时器或清除已选择的 BSSID。
  开机择优扫描与网页扫描共用互斥锁；忙碌时网页提示稍后重试。
  扫描为空时返回成功和空数组；失败路径释放扫描结果，避免占用驱动内存。
- 系统信息、亮度、声道、音频输出、天气及按需加载的双 DAC 配置共用最多
  2 个并发读取名额。名额保持到响应正文解析完成，每个实际请求超时为 10 秒；
  失败后继续处理队列。后续配置回读与状态轮询也使用同一队列。

已连接时使用驱动的后台扫描行为，依据
[ESP-IDF Wi-Fi 扫描说明](https://docs.espressif.com/projects/esp-idf/en/v5.5.3/esp32s3/api-guides/wifi.html)。
这消除了应用主动断连；跨信道扫描仍会占用无线时间，不能据此保证播放完全无抖动。
当前 HTTP 扫描处理器仍同步等待结果，扫描期间其他 HTTP 请求可能等待。

## 后续优化优先级

以下结论来自本仓库代码审查；尚未进行板上延迟、内存或音频连续性实测。

| 优先级 | 代码依据与问题 | 建议与验证方式 |
| --- | --- | --- |
| 按需 | 扫描已取消主动断连，但 `web_server.c` 的扫描处理器仍同步等待 | 如果实测扫描期间网页响应仍慢，再考虑异步扫描任务和结果缓存；先测 AirPlay 连续性和 HTTP 最大延迟 |
| 暂缓 | `serve_spiffs_file` 以 1 KB 分块读取，未设置压缩、ETag 或缓存校验头 | 用户确认设备仅在局域网低频访问，本次不实现 gzip 或缓存优化 |
| P2 | 每次照片预览会分配灰度、抖动工作区和输出数组，并在主线程执行逐像素处理 | 复用缓冲区；若手机实测仍有卡顿，再将抖动移到 Worker。记录拖动时帧耗时与大照片解码内存峰值 |

美化后的页面在增加网页更新入口前，原始大小约 37 KB；本地 gzip 压缩估算
约 10.7 KB（约减少 71%）。
当前固件仍传输原始 HTML，压缩收益尚未实现。增加分块大小前应测量任务栈余量，
现有发送缓冲区在栈上，不能只按吞吐量调整。

## 通过网页更新配置页

在「更新网页」卡片中选择项目的 `data/www/index.html`，点击「上传并更新网页」。
页面显示上传进度，并在上传后重新读取设备首页核对内容；确认一致后才显示
「重新加载新版页面」。更新不需要重启设备。点击重新加载前，请保存其他配置。

入口接受非空 `.html` / `.htm` 文件，上限 65,536 字节，检查完整 HTML 的基本结构。
只更新首页，不上传其他页面、样式文件或固件。`.bin` 文件继续使用「固件更新」。
校验 HTML 结构不能保证任意第三方页面能正常配置设备，应使用本项目页面文件。

设备固件须包含 `POST /api/fs/upload` 接口。旧页面没有该按钮时，需要先安装一次
新版首页：可使用对应环境的 `uploadfs`，或在项目根目录通过已有接口上传
（把 `DEVICE_IP` 替换为实际设备地址）：

```powershell
curl.exe --fail-with-body -X POST "http://DEVICE_IP/api/fs/upload?path=/spiffs/www/index.html" --data-binary "@data/www/index.html"
```

上传成功后刷新浏览器，以后即可使用网页入口更新。新固件先写临时文件，检查
写入、关闭、长度和回读 CRC，再通过备份替换目标文件；传输失败保留旧文件。
新版页面还会提交文件 CRC32。启动时恢复中断的替换并清理临时文件。
这些保护需要本次新固件；旧固件仍直接覆盖文件，建议先更新固件，再上传首页。
新入口在 HTTP 错误、响应异常、超时或内容核对失败时不会提示成功或自动刷新。

## 2026-09-16 稳定性与性能优化

### 天气刷新

- 配置保存和手动刷新交由天气任务执行，HTTP 回调不再同步等待 HTTPS 重试。
- `POST /api/weather/refresh` 成功返回 HTTP 202，表示已接受；相同刷新请求在
  排队或执行期间合并。`GET /api/weather/refresh` 返回 `pending`、`running`、
  `completed`、`success` 和 `error`，其中后两项描述最近完成的获取结果。
- 配置更新期间的旧响应不会覆盖新配置的数据；天气与空气质量先解析到临时
  快照，完成后统一发布。天气 JSON 和响应缓冲在请求空气质量前释放。
- HTTP 响应体限制为 64 KiB，缓冲显式分配在 PSRAM；超限和内存不足为持续错误，
  即使 HTTP 库忽略事件回调返回值也不会解析不完整响应。
- SNTP 重配置也由天气任务处理。网络失败时保留上一次成功的天气数据。

### 文件上传与 OTA

- 文件上传检查接收、短写、关闭、可选的 `crc32` 参数和回读 CRC；临时文件验证
  成功后才替换现有文件。`.uptmp` 和 `.upbak` 为保留后缀，不接受外部文件操作。
- SPIFFS 不支持直接覆盖重命名，因此先备份旧文件，再安装新文件；失败尝试
  回滚，启动挂载时恢复遗留备份。需要同时容纳新旧文件的空闲空间。
  此机制不等同于文件系统的掉电原子事务，仍需实机断电测试。
- OTA 页面检查 HTTP 状态、JSON 结果和超时；失败恢复按钮，不再把断网当成功。
  写入后轮询系统信息，只有运行固件的 ELF SHA-256 标识匹配、启动标识发生变化，
  才提示升级完成。同一版本再次刷写也需要确认一次新的启动。
- 固件和首页均需更新才能获得完整行为；未改变页面布局。

### 音频队列

- 排序索引改成循环数组，正常出队和溢出淘汰不再搬移整个索引数组。
- 顺序到达的音频帧直接追加；乱序帧仍保持 RTP 时间戳排序及回绕比较。
- PCM 复制在取得独占槽位后移出临界区；FLUSH 递增代次，拒绝发布复制期间
  已失效的帧。生产者和消费者持有的槽位不会被 FLUSH 或溢出淘汰复用。
- 二值信号量只用于唤醒；锁内帧数决定是否可取，避免 FLUSH 与计数信号量失配。
  未缩小音频缓冲容量；实时收益仍需板上测量。
